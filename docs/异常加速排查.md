# X 轴长直线运动中偶发加速：检查记录

## 已知现象

用户报告：运行正式扫描时，X 轴在一条长直线途中突然明显加速一段，随后恢复正常，共出现两次；之后观察运行正常。用户说明使用的是发布项目，将 `SCAN_SPEED_UM_PER_SEC` 改为 2000（2 mm/s），并修改过 Y 方向。

当前仓库默认配置仍是 1000（1 mm/s）和 `Y_STEP_DIRECTION=0`，未取得那次实际烧录的二进制及参数副本。本记录分析的是仓库源码及用户描述，不能替代事发串口、位置或速度记录。

## 源码检查结论

1. [SnakeScan / Scan_MoveRelative](../firmware/Core/Src/main.c) 在每条 X 行开始时调用一次 `Emm_V5_Pos_Control`；随后 `Scan_WaitAxisReached` 每约 500 ms 查询状态，没有在 X 行中途重新下发更高速度的分支。
2. 两轴共用编译期常量 `SCAN_SPEED_RPM`。导程 1 mm/圈时，2000 μm/s 对应 120 RPM；修改 Y 方向不会修改 X 的速度字段。
3. `SCAN_ACCELERATION=0` 表示不使用加减速曲线、直接按设定速度启动，能影响启动瞬间，但不能直接解释长直线中间偶发的一段加速。
4. [Emm_V5_Pos_Control](../firmware/BSP/Emm_V5.c) 的发帧缓冲是 `static`，不是返回后失效的栈数组。不能仅因为使用 DMA 就断言存在“局部变量失效导致随机速度”的错误。
5. 等待回复超时后，当前位置命令不会自动重发。串口恢复主要发生在状态查询接收失败时，未发现“查询失败就加速赶进度”的策略。

**因此：没有发现明确的途中主动改速代码，但尚不能排除软件/通信、驱动器内部控制或机械、电源方面的偶发问题。** 之后正常不意味着已经找到并消除了原因。本次整合不修改运动逻辑，也不宣称已修复该现象。

## 值得核查的代码边界

- UART 接收回调在标记一帧后，立即对同一接收缓冲重新启动 DMA；主循环复制时只关闭 CPU 中断，DMA 并不会因此停止。在突发/连续回复条件下存在帧被覆盖的风险。它更直接影响状态和换轴判断，**不能据此直接解释 X 的设定速度变大**。
- 协议函数没有把 `HAL_UART_Transmit_DMA` 的返回状态传到扫描层；在发送忙或错误时诊断信息不足。现有主循环调用间隔较大，未证明此项在事发时出现。
- 当前使用固定 `0x6B` 字节校验形式，不能提供 CRC 那样的数据检错能力。应按驱动器实际设置核对协议和线路质量，不能只看末尾有 `0x6B` 就认为整帧内容可靠。
- 到位判断主要依赖状态位与曾经看到未到位状态，未同时记录实时速度、位置误差、堵转和驱动状态。短行以及异常回帧的情况也需要单独验证。

DMA 是异步传输；缓冲所有权与完成时刻需由软件保证。相关 API 行为可核对 [ST 官方 HAL UART 源码](https://github.com/STMicroelectronics/stm32f1xx-hal-driver/blob/master/Src/stm32f1xx_hal_uart.c) 和本项目携带的 HAL 实现。这里列出的是可审查的实现边界，不是已确认的事故根因。

## 下次怎样定位

先检查丝杆/导轨是否卡滞、联轴器和负载是否稳定、电源与接线是否松动。先用较短行程、低速、有人观察的方式验证，确保能直接切断动力，不以长时间无人值守扫描复现异常。

最有区分力的是同时记录以下三类证据：

| 记录 | 要看什么 |
|---|---|
| MCU 发出的串口 TX | 加速前后有没有新的 `0xFD` 位置命令或 `0xF6` 速度命令；速度字段是否变化 |
| 驱动器反馈/显示 | 实时速度、目标位置、实际位置、位置误差、报警/堵转状态及驱动器固件/运行模式 |
| 运动现场与测量 | 带时间的视频、是哪一行/位置、有无先变慢/卡住再快速追上、电源状态和同时段原始电流 |

可使用串口监听或逻辑分析工具被动记录。抓 RS485 总线时要区分主机发送与从机回复；不要让第二个上位机同时向同一电机发送控制命令。记录时间尽量与源表同源，或保存明确同步事件。

在地址 X=2、首行方向=1、导程 1 mm、16 细分、速度 2 mm/s、行长 100 mm 这些条件下，代码应构造如下位置帧：

```text
02 FD 01 00 78 00 00 04 E2 00 02 00 6B
         └───┘    └─────────┘
        120 RPM   320000 pulses
```

这只是上述明确参数下的预期帧，不是事发时已捕获的帧。另一方向相应改变方向字节。运动途中正常轮询应是状态查询，不应不断出现新的更高速运动命令。

## 根据证据区分方向

- 如果抓到新的更高速度命令：追查实际烧录版本、所有发命令来源和串口帧内容。
- 如果目标速度不变，但实际速度/位置误差先异常再恢复：重点检查驱动器闭环控制、负载/卡滞及电源；“误差积累后追赶”只能作为待验证解释。
- 如果驱动器速度稳定，仅通过声音感觉变快：用尺标视频或实际位置变化进一步确认，避免把声音变化当作定量速度。
- 若只在掉头发生：另查启动曲线和回差；这与用户本次描述的 X 长行中途现象应区分记录。

建议保存 [事件 CSV 模板](motion-event.template.csv)、实际配置头文件、HEX/AXF 与提交号、源表原始数据和驱动器菜单照片。需要新增日志或调整接收缓冲时，应作为独立固件变更先编译、再短行程验证，不能只靠改一个速度或加速度常量宣布解决。

## 对图像重构的影响

当前位置映射假设有效横扫内匀速。若一段真实速度突然变化，等时间或等点数的像素就不再代表等距离，会产生局部拉伸、压缩或边缘错位。发生过异常的扫描应标记并保留原始记录，优先重扫；若有同步位置反馈，可据此扩展位置映射，不能只通过二维平滑掩盖。
